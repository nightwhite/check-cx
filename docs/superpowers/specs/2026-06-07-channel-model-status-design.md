# 渠道 + 模型状态页设计规格

## 目标

将当前首页改造成更专业的状态页：按渠道展示模型，每个模型展示一排检测历史状态格，用户能快速判断不同渠道下同一类模型的可用性和稳定性。

## 用户与关注点

页面用户是需要选择或排查 AI 模型调用渠道的人。他们关心：

- 哪个渠道当前可用
- 某个渠道下哪些模型异常或延迟
- 异常是偶发还是持续
- 最近一次延迟、可用率和更新时间

前台文案只表达运行状态，不暴露开发实现、配置逻辑或数据库概念。

## 信息层级

采用已确认的层级：

1. 总览状态：所有监控模型整体状态、最近更新时间、统计摘要
2. 渠道区块：例如 `Claude 官方`、`AWS Bedrock`、`OpenRouter`
3. 模型行：例如 `Claude 3.5 Sonnet`、`Claude Opus`
4. 历史状态格：每个模型下方或右侧展示一格一格的最近检测状态
5. 模型详情：点击模型行后展示最近检测、错误信息、端点、延迟趋势

## 首页布局

推荐桌面布局：

- 顶部展示整体状态 banner
- 下方按渠道纵向排列区块
- 每个渠道区块头部展示渠道名称、渠道整体状态、模型数量
- 每个模型是一行
- 模型行左侧展示模型名、最近延迟、可用率
- 模型行右侧展示一排检测历史格
- 行尾展示当前状态文字

移动端布局：

- 渠道区块仍纵向排列
- 模型名在上，历史格在模型名正下方
- 当前状态和延迟放在模型名右侧或下一行

## 历史状态格

状态格表达最近检测历史，不表达配置项。

- 绿色：正常
- 黄色：延迟或降级
- 红色：异常
- 蓝色：维护中
- 灰色：无数据

默认沿用当前系统最近 60 次检测数据。鼠标悬停或点击单格时可展示检测时间、延迟、错误摘要。

## 数据映射

短期不引入新数据模型。

- 当前 `groupName` 作为渠道名展示
- 当前 `providerTimelines` 作为模型检测列表来源
- 当前 `timeline` 数组作为历史状态格来源
- 当前 `availabilityStats` 作为可用率来源
- 当前 `latest` 作为模型行当前状态来源

后台仅需将“分组”在 UI 文案上调整为“渠道”，不改变表结构。

## 交互

- 渠道区块默认展开
- 点击模型行打开详情抽屉
- 搜索可匹配模型名、渠道名、Provider 类型、端点
- 顶部筛选可按渠道过滤
- 状态格悬停显示具体检测信息

## 非目标

本次不做：

- 新增 `channels` 表
- 事故公告系统
- 订阅通知系统
- 多区域复杂建模
- 自定义域名或品牌设计大改

## 验收标准

- 首页按渠道分组展示模型
- 每个模型下方或右侧有历史状态格
- 同一模型可在不同渠道下分别显示
- 空数据时页面仍能清楚表达“暂无监控模型”
- `pnpm typecheck`、相关组件测试通过
